## What is measured

Each scenario starts from a **real spec from the ONP domain** (class enrollment, student grades) and seeds **a defect that really plagues spec-driven projects**. It measures whether each tool detects the defect **mechanically** — what a CI pipeline catches on its own, without a human or LLM in the loop. That detection is what keeps the spec *true over time*.

## Defect class descriptions

- **CLEAN_BASELINE** — correct spec — no tool should raise a false positive
- **REQ_NO_TEST** — requirement with no test that proves it (SDD drift #1)
- **ORPHAN_TEST** — requirement renamed; test was left behind pointing to the old ID
- **INCOMPLETE_REQ** — requirement with no observable behavior (no Given/When/Then)
- **PREMATURE_DONE** — task marked done with no proof of a passing test
- **SILENT_ASSUMPTION** — product decision assumed with no explicit record
- **PRIVACY_VIOLATED** — student grade exposed / PII in a log — violates the constitution
- **ORPHAN_CODE** — code file that serves no requirement at all
- **BROKEN_REF** — task references a requirement that doesn't exist
- **DUPLICATE_ID** — two requirements with the same identifier

## Why the competitors fall behind

- **OpenSpec** has a real structural validator (it requires a normative SHALL sentence and at least one scenario per requirement), so it catches `REQ_INCOMPLETO`. But its model has no notion of **tests, proof, assumptions, privacy, or orphan code** — so there is no way to detect drift #1 (requirement without a test), premature "done", the silent assumption, or the privacy violation.
- **spec-kit** is scaffolding: it generates great templates and steers the agent, but runs no defect check at all — and in its template **tests are optional**. Mechanical detection: zero.

onp-spec-driven is the only one that treats **test proof, assumptions, and principles as first-class data** and audits them mechanically — that's why it detects classes the others don't even represent.
